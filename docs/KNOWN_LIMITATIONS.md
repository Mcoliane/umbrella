# Known Limitations

- Local process supervision is script-managed; no built-in launchd/systemd units yet.
- Contract tests may fail in restricted sandbox environments due to local socket bind limits.
- Runtime dependency lock currently pins Python tooling only; service code is standard-library based.
- No hosted update channel yet; upgrades are manual via installer/release artifacts.
- No GUI onboarding flow; CLI-first experience.
- Short-term **town conversation** memories auto-promote via nominate-then-distill: a recurrence sweep (`POST /v1/promotions/sweep`, triggered opportunistically by session after capture) nominates knowledge appearing in two or more different towns, and session curates nominations through the same Layer 2 distiller as conversation facts before writing — nothing enters long-term memory undistilled. Curation needs the model provider; without one, nominations wait. Short-term `memory-core` entries (execution working memory) still require explicit promotion; queued promotions drain automatically once enqueued.
- The plugin/skills runtime is implemented, but it does not sandbox plugins. Skills get process *separation*, not isolation: they run as ordinary local subprocesses under the plugin-host service user, with full filesystem and network access. The manifest `executionPolicy` fs/network/isolationProfile fields are validated and recorded, never enforced — every invoke response says so in `policyWarnings`, and `GET /v1/plugin-host/health` reports `isolation: none`. The optional `docker`/`podman` container runtime was removed rather than left as an unused implied guarantee — it was broken on its default path, unused by anything shipped, and added an external dependency the project chose not to carry. That was a dependency decision, not a technical impossibility: containers run fine on both supported platforms, and the path can be restored if untrusted plugins ever become a goal. Be precise about what protects you today, because it is less than it sounds:
  - **The policy engine's approval gate does not fire in the default configuration.** Autonomy defaults to `auto` (`services/policy/app.py:343-344`), and the approval check short-circuits unless the mode is not `auto` (`:583`). This is a deliberate pre-launch default, not an oversight. Setting `ask` does not currently turn it into a prompt either: the session and TUI have no approve/deny surface, so policy returns `action_approval_required` as a denial. Arming this properly requires building that handshake first.
  - **Catalog trust verification is also off by default**: the launcher spawns catalog without `--signature-mode` (`scripts/control-plane/manage-platform-stack:406`), which defaults to `permissive` (`services/catalog/app.py:1021`), where every item evaluates as trusted.
  - What *does* work: the orchestrator's plan-declared approval flow (`requiresApproval` → approval service → resume), which is contract-tested end to end; mesh auth, which is closed by default on all services; and the execution policy's timeout, env-allowlist and I/O caps.
  Treat this as a single-operator tool running code you wrote or vetted. It is not currently a boundary against code you do not trust.
- Approval for dynamic actions is policy-aware, but first-class human approval UX is still centered on run/step approval flows rather than a dedicated interactive skill-approval surface.
- Shop profiles and runtime session state are persisted under generated observability paths; they are not yet promoted into a more formal operator-managed configuration model.
- Runtime capability routing is implemented, but runtime-family telemetry is still basic summary metadata rather than a full observability dashboard with counters and historical trend views.
